0.3 对 1.0 的实质影响（登记）

§0.2 的裁决不是纯 UI 改动：下列两项改动了 1.0 的数值路径或判据口径，须单独登记。

  1. A8 必须开显式例外（拆除核销所致）。契约 §8.4 :1854 现为 |ΔM − (NewCapital + 诊断注入)| ≤ max(1e-3, 1e-8×货币存量)； 拆除会销毁货币，故须改为 ΔM == NewCapital + Infusion − Δ(累计核销)， 并保留"未申报的货币减少仍然违规"这一更强的形式（详见 §六-1）。 收益：1.0 的 A8 是"构造性恒真"（两侧同源 TotalMoney，判别力 ≈ 0）； 加上申报口径后它能区分"申报核销"与"漏记一条腿" ⇒ 判别力比 1.0 更强 （该结论的实测依据见 out/review/REVIEW-FINAL.md §3）。
  2. §4.4 建筑自动缩编保持冻结（DecayFrozen=true），拆除由玩家手动触发。 两者互补；不得为了拆除而把 DecayFrozen 翻回 false（那会同时改变 AI 侧行为）。 唯一例外：在对照审计中显式注入 DecayFrozen=false（沿用 audit_tasks_test.go:259 的写法）。

一、版本目标

把"单政府 + 无 UI + 批处理"变成"玩家作为政府 + HTML 界面 + 逐帧推进"， 保持 1.0 数值路径逐位不变。

  1. 现有"控制台 + 批处理"的模拟迁移到图形窗口内运行；
  2. 绘制三个主面板（市场 / 建筑列表 / 建造队列）与一个杂类总表页（其他）；
  3. 提供基本可玩操作：调速与暂停、手动建造与拆除、调节 AI 扩张参数；
  4. 落地决策来源接口，使"玩家接管"与"AI 托管"是同一接口的两个实现——这是 2.0 复市场的结构前提（§0.2-9）。

⚠️ "保持核心模拟逻辑完全不变"须读作：UI 不改变 §8 主循环的顺序与算式。 玩家动作本身会改变经济结果（这是玩法），但它必须经由 book 的既有记账腿进入， 不得新增未经声明的货币腿（唯一例外：§三-3 的拆除核销）。

三、玩家动作

每个动作一行：前置条件 / 记账腿 / 收敛性 / 生效时机。 记账腿一栏必须逐条写死——这是"玩家 = 政府"能保住 A8 的关键。

#动作前置条件记账腿生效时机
1建造（x1/x5/x10）显式建筑；不超上限（完工时裁剪）；不绕过 AvailableCash复用既有 G2 路径：book.PurchasePower + 完工归属立即
2置顶该订单存在且未被置顶无（仅改顺序）立即
3拆除显式建筑（Produces() && !IsNonMarket() && !IsAgent）；仅政府级新增 book.DemolishBurn：借 建筑池余额 / 贷 销毁账户；在途订单取消不退款立即
4调速 / 暂停—无（不改状态）立即
5调参参数在 §0.2-11 与 §0.2-9 的白名单内无立即
6查看—无（只读）—

§三-1 与 §三-2 的关系：玩家建造不绕过现金约束，仍受 AvailableCash 限制（fiscal.go:230）； "置顶"只改队列顺序（优先级：玩家 > §4.2 预警插队 > FIFO）。 §三-3 的核销：建筑池允许透支（step.go:1496），故余额可能为负； 负余额核销 = 销毁一笔负债 = 货币总量增加。建议统一称"核销"并采用带符号额（§0.2-16）。

  • 玩家建造的行为规则：置顶、除上限外无条件入队（见 §0.1 与 §三）。

  • 每页 20 条建造请求；左右键翻页并标注页数；
  • 每条：建筑类型 / 已建部分 ÷ 总建造力 / 剩余时间。

五、时间与确定性

  • 渲染 60 FPS；逻辑按 "每秒推进 tick 数" 驱动（§0.2-11 / §0.2-12）；
  • 帧与 tick 解耦：同一参数下，tick 序列必须与帧率、倍速无关。 这不是洁癖——本项目刚在 ledger.sortedAccounts() 修好"同二进制逐位一致"， 若让帧直接驱动 tick 就会重新打破该保证（ledger.go:381-394）。
  • 实现建议：逻辑侧维护累计时间（或帧计数）来决定本帧是否 Step()，不把倍速写进引擎参数。
