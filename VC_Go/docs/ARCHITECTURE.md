## 0. 结论摘要（决策矩阵）

| 编号 | 决策项 | 结论 | 一句话理由 |
|------|--------|------|-----------|
| D1 | 核心语言 | **Go**（`go 1.22+`） | 编译快、单二进制、并发调参天然、生态足够；内核无第三方依赖 |
| D2 | 架构形态 | **确定性 tick 内核 + 可选 Web 呈现层（TS）** | 内核零 UI 依赖，可 headless 回归；呈现层后续独立演进 |
| D3 | 数值表示 | **定点整数 `int64`，刻度 1e-3**（钱/量/价），中间量用 `float64` | 跨平台逐位可复现，消除浮点漂移，回放校验可做 hash 断言 |
| D4 | 数据驱动 | **全部商品/建筑/配方/消费组/参数外置为 JSON**，内嵌 `go:embed` 兜底 | 数值调参不需重编译，mod 与后续版本扩展无需改代码 |
| D5 | 求解器 | **RK4 固定步长 `dt`，每 tick 内 `n_sub` 次子步** | 文档只要求 `dt=0.5`；显式欧拉在欠阻尼下不稳，RK4 给相同稳定性 |
| D6 | 求解模式 | **双模式**：`ODE`（时间演化，默认）/ `CLEARING`（每 tick 直接解均衡） | 调试期用 CLEARING 剥离振荡拿到"终态"，上线用 ODE 保留真实动态 |
| D7 | 劳动力建模 | **从 1.0 起即按"阶层-岗位"建模**（劳动力/工程师/资本家） | 3.0 人口系统直接继承同一张表，避免 3.0 结构性重写 |
| D8 | 结构状态 | **建筑"等级"为唯一资本存量状态**，土地为约束而非市场 | 1.0 无地价；土地市场推迟到 2.x 区域系统，成本最小 |
| D9 | 时间语义 | **1 tick = 1 周，1 年 = 52 tick**；文档"52 周期"就是 1 年、"156 周期"= 3 年（见 §4.0） | 与 README 的 52 周数据契约一致；文档的 5%/**周期** 一律重列读作 5%/年，按 52 折算 |
| D10 | 求解器实现归属 | 内核纯 Go，**不引入 BLAS/无 CGO** | 系统规模是稀疏小矩阵（11×11 商品），手写消元比外部库更快且更可控 |
| D11 | 并发策略 | **tick 内单线程顺序执行**；并行只在"多组参数批量跑"外层 | 保证确定性；性能瓶颈在 ODE 与配方求和，量级极小 |
| D12 | 呈现层 | 阶段 1.0 只做 CLI 报告 + CSV 时序导出；Web 面板归 1.1 | 先证明经济收敛，再做可视化，避免过早耦合 |

## 1. 目标与非目标

### 1.1 总目标
构建一个**宏观-微观混合、以微分方程整体建模替代微观代理**的经济模拟内核：生产与市场由连续 ODE 描述，资本形成（扩建/拆除）由离散事件描述，二者构成混合动力系统；在自由进入-退出下，**利润率被压入扩建阈值带并在其中达到有界稳定**（原"长期利润趋近于零"目标已废除，见 rev 4 与契约 §8.4）。

### 1.2 架构层面的非功能目标

| 目标 | 指标 | 验证方式 |
|------|------|----------|
| 确定性 | 同输入 + 同种子 → 逐位相同结果 | 结果 hash 断言测试 |
| 可回放 | 事件日志可重放到任意 tick | replay 测试 |
| 性能 | 10,000 tick × 3,000 建筑的整跑 < 200 ms | benchmark 门槛测试 |
| 可调参 | 数值参数改动零重编译 | 数据加载测试 |
| 无隐患停机 | 任何 tick 不产生 NaN / 负库存 / 负价格 / 溢出 | 不变量（invariant）断言 |
| 可扩展 | 加一种商品/建筑/消费组只改 JSON + 至多一个 hook | 扩展性验收用例 |

### 1.3 非目标（1.0 明确不做）
- 图形渲染、地图、单位与战争。
- 多区域贸易、运输成本、关税（归 2.x）。
- 完整货币、银行、利率、汇率（1.0 只留接口，归 1.2/2.2）。
- 玩家 UI 交互与存档读档（归 1.1）。
- 技术与科技树、政治与法律（归 3.x）。

## 2. 分层与模块架构

```
┌──────────────────────────────────────────────────────────────┐
│ L4 呈现层  cmd/sim（CLI 报告/CSV）  web（1.1+ 仪表盘）          │
├──────────────────────────────────────────────────────────────┤
│ L3 用例层  pkg/sim       tick 编排、不变量校验、快照、回放      │
│            pkg/report    指标聚合、时序导出、收敛判定           │
├──────────────────────────────────────────────────────────────┤
│ L2 系统层  pkg/market    价格 ODE 求解与出清                    │
│            pkg/production 配方、投入产出、短缺惩罚              │
│            pkg/labor     阶层、雇佣、工资                       │
│            pkg/consume   财富等级、消费组、购买顺序、满足度      │
│            pkg/build     建造队列、建造力分配、土地约束          │
│            pkg/ai        利润驱动扩建/缩编策略                  │
│            pkg/money     货币接口（1.0 直通实现，1.2 替换）      │
├──────────────────────────────────────────────────────────────┤
│ L1 领域层  pkg/model     实体与不变量（纯数据，无逻辑）          │
│            pkg/num       定点数、区间、确定性累加               │
│            pkg/data      数据表加载/校验/内嵌兜底              │
├──────────────────────────────────────────────────────────────┤
│ L0 基础层  pkg/eventlog  结构化事件日志（回放与调试）

**依赖方向严格单向 L4 → L0**，`pkg/model` 与 `pkg/num` 不依赖任何上层，禁止循环依赖（用 `go vet` + 依赖图测试守护）。

### 2.1 各模块职责与对外契约

| 模块 | 职责 | 对外关键接口（草案） | 依赖 |
```

## 3. 领域模型与数据表

### 3.1 实体关系

```
Tables(静态)                    State(动态)
├─ Goods[11]                    ├─ Markets[11]      {price, dprice, refPrice, demand, supply, E}
├─ BuildingTypes[11]            ├─ Buildings[N]     {typeId, level, cash, staff[3], hireRate, idleTicks}
├─ Recipes[11]                  ├─ ConstructionQueue[] {typeId, units, progress, cashClaim}
├─ ConsumptionGroups[4]         ├─ Population       {cohorts[3], wealthLevel, satisfaction}
├─ Uses[商品×消费组]             ├─ Land             {arable, arableUsed, coalCap, ironCap}
├─ DemandPer100k[财富×消费组]     └─ Tick             {n, rng, gdp, avgWage}
├─ Params(全局)
└─ Regions[1]  ← 1.0 单区域占位，2.0 扩展为 N
```

**关键建模选择：**
- `Building` 是唯一的资本存量载体，`level` 是唯一的规模状态（不再有"每级子实例"）。
- 每个**建筑类别**一条市场线：同类建筑的投入/产出合并到商品维度，避免 3,000 个实例各自定价。
- 自给农场不是实体，而是由 `Land.arable - arableUsed` **派生**的虚拟产出，见 §5.3。

### 3.2 数据表清单（`data/`，全部 JSON）

| 文件 | 内容 | 关键字段 |
|------|------|----------|
| `goods.json` | 11 种商品 | `id, name, category(necessity/raw/industrial/service/special), initPrice, priceFloor, priceRef, demandSlope(b), supplySlope(d)` |
| `buildings.json` | 11 种建筑 | `id, name, buildCost(power), maxLevelCap, landType(grain/cotton/coal/iron/none), laborPerLevel[3], cohortWages[3], baseOutput, autoScaleRate` |
| `recipes.json` | 每建筑投入/产出 | `buildingId, inputs[{good, qty}], outputs[{good, qty}], perLevelQty(默认5000人基准)` |
| `consumption.json` | 4 消费组 + 使用价值表 | `groups[{id, name, needs[]}], uses[{good, group, value}]` |
| `demand.json` | 财富等级基准需求 | `tiers[{wealth, per100k{group: qty}}, interp: linear]` |
| `population.json` | 阶层构成与工资 | `cohorts[{id, share(0.75/0.20/0.05), wage(5/10/20)}], perLevelWorkers(5000), hireStep(0.05), hireWindow` |
| `params.json` | 全局常数 | `ode{k, rho, dt, nSub, mFloor}, growth{t0:75%, lo:0%, loRate:-20%, hiRate:+5%, ticksPerYear:52}, expand{threshold:10%, per5pct:1, maxRatio:10%}, build{powerPerSite:30, queueWarnTicks:52}, decay{trigger:75%, window:156, rate:5%}, gdp{mode:doc\|flow\|production}, floors, tolerances` |

## 4. 数学模型规范化

### 4.0 时间语义（必须先统一）

1.0 文档中的"周期"存在**数量级自相矛盾**，架构上必须钉死：

| 文档原文 | 判断 |
|----------|------|
| "队列 >52 周期" | 52 周期 = 1 年 → 支持 **1 周期 = 1 周** |
| "连续 156 周期 = 52×3" | 52×3=156 一致 → **强证据：52 周期 = 1 年** |
| "人口增长率（每 52 周期）+5%" | 52 周期 = 1 年 → 年增 5%，合理 |
| "利润率 > 0：尝试增雇 5%"（**每周期**） | 若字面按周计，52 周后雇工量 = `1.05^52 ≈ 12.6 倍/年`，经济瞬间爆炸 → **必须按年率折算** |
| "价格 ODE 步长 dt=0.5" | 与周为单位的 tick 相容（tick 内 10 次子步，等效步长 0.05），无需改口径 |

**定案（架构约束 T1，rev 2 已修正）**：
- 采用 **`1 tick = 1 周`、`1 年 = 52 tick`** 的内部时间单位。依据：文档"156 = 52×3"是唯一无歧义的算术证据；且与 README 的 52 周数据契约（`52-week demand`、`rolling 52-week means`）一致。
- 文档的"52 周期"**就是 1 年**（建造队列告警）；"156 周期"**就是 3 年**（缩编窗口）。无需重释。
- 文档的"每周期增雇/解雇 5%"改为 **年化 5%**，每 tick `5%/52 ≈ 0.096%`，由 `population.hireStep`（存年率）表达。
- 文档的"每 52 周期 +5% 人口"即 **每年 +5%**，每 tick `+5%/52`。
- 所有"每周期 X%"型参数在数据表中统一以 **年率** 存储，由引擎按 `growth.ticksPerYear` 折算。调参语义唯一，不再出现两套口径。

> **口径风险提示**：以周为 tick 后，模型的时间粒度变细，但 §10.3 的规模失衡问题**不会因此消失**——那是"产出量 × 单价"对"雇佣量 × 工资"的比例错配，与时间单位无关。另需注意：10,000 tick 在周口径下等于 **192 年**，收敛窗口非常充裕；若标定发现"每周期"量级本应按年计，把 `ticksPerYear` 调成 1 即可，其余设计不变——这正是把它做成参数的原因。

### 4.1 市场方程（文档 §2 的形式化）

需求/供给/过剩需求：

```
D = a·(P/P₀)^(−ε)    a = α·Pop          (α 为零利润价下人均消费量)
S = S_fixed          (建筑实际可售供给，阶梯常数；等价于原式 d = 0)
E = D − S
```

价格动力学（二阶）：

```
m·P̈ + ρ·Ṗ = E + F_ext
K(P) = −E′(P) = (ε·a/P₀)·(P/P₀)^(−ε−1)     (局部刚度，即原文的"回复力系数")
m = K(P)·T²/(4π²)     ρ = ζ·K(P)·T/π
ζ = ρ / (2·√(m·K))
```

> **rev 3 修订**：原文的 `b·(P − P_ref)` 项已删除。`E` 中已含 `D` 对 `P` 的回复力，再加一项是重复计数，实际生效刚度会变成 `2b+d` 而非 `b`，使 `T`、`ζ` 的公式与真实动力学不符（探针 `VC_Go/tools/spring_price_probe.js` 实验 1）。锚定改由 §3.4 的零利润价 `P_cost` 承担，`P₀ ≡ P_cost`。

**求解器实现（架构层补充）**：

1. 状态向量 `y = (P, Ṗ)`，`ẏ = (Ṗ, (E + F_ext − ρ·Ṗ)/m)`。
2. 使用 **RK4**，固定步长 `dt = params.ode.dt / nSub`，每 tick 做 `nSub` 次子步。文档要求 `dt=0.5`，默认 `nSub=10`（等效步长 0.05），稳定性由 §10.1 的门槛测试兜底。
3. **刚度与惯性标定（T2，rev 3）**：`K(P) = −E′(P)` 随价格变化，每 tick 用当期价格重估；`m = K(P)·T²/(4π²)`，`ρ = ζ·K(P)·T/π`。数值保护改为 `m ≥ K(P)·(h/2.8)²`（RK4 虚轴稳定边界），并要求 `ω·h ≤ 2.8`（`ω = √(K/m)`）。**不再使用 `m = k·G`**：`G` 是内生量，`m ∝ G` 会让 `T` 与 `ζ` 随经济规模持续漂移（`VC_Go/tools/spring_price_scale.js` 附录已量化），且 `G → 0` 的除零问题一并消失。低价端 `K ∝ P^(−ε−1)` 上升，是全区间最刚处，`nSub` 按当期 `K` 自适应。
4. **价格上下限（T3）**：`P ∈ [priceFloor, priceCeil]`，触碰边界时钳制并把 `Ṗ` 置 0（模拟涨跌停），同时记录 `clampEvents` 计数。文档未定义地板价，但不加会导致 `P<0` 与"售价为负即无限需求"的病态。建议 `priceFloor = 0.2·P_cost`、`priceCeil = 5·P_cost`。
5. **锚定（T4，rev 3）**：`P_ref` 项已从方程中删除；锚定由 §3.4 的零利润价 `P_cost` 承担——它由 §3.3 投入产出表 + §5 工资表解 Leontief 价格方程 `p = (I − Aᵀ)⁻¹·l` 得到，而不是"上一轮的稳态价"（后者会随重定价漂移，正是 R2 的成因）。

**平衡态（论文级显式解，用于单测）**：

`P̈ = Ṗ = 0` ⇒

```
P* = P₀ · ( a / (S − F_ext) )^(1/ε)
```

存在且唯一的**正解条件**：`F_ext < S`（否则 `E > 0` 在任意价格下成立，价格一路顶到 `priceCeil`，进入"产能不足"分支）。**标定恒等式** `a = S ⇒ P* = P₀ = P_cost`，该规则与 `ε` 无关，是价格表的验收条件。`P*` 对产能的敏感度为 `−1/ε`，这是量价弹性调参的核心旋钮。

**CLEARING 模式**：直接令 `P = P*`（每 tick 解一次，`c` 用当期实际供给），用于参数扫描与"终态"验证；ODE 模式用于动态、振荡与危机测试。两者共享同一套 `E` 计算，避免双实现不一致。

### 4.2 供给与产能

```
S_fixed(g) = Σ_overBuildings  hireRate_b · q_output(b,g) · level_b · shortageFactor_b
```

- `hireRate_b ∈ [0,1]`：实际雇佣 / 满编，见 §5.1。
- `q_output(b,g)`：单级每 tick 产出（由 `recipes.json` 的基准换算）。
- `shortageFactor_b ∈ [0,1]`：原料短缺惩罚，见 §4.3。

文档把雇佣率写成 `L_used / L_capacity` 再乘 `q·N`，与上面的 `hireRate · q · level` 等价；架构上把 `level` 与 `hireRate` 分离存储，便于分别做缩编与解雇。

### 4.3 原料短缺惩罚与投入分配（T5）

文档要求"所需原料 100、市场仅 80 → 产出降至 80%"。但若**多个建筑同时超需求**（总和 > 100），必须定义分配规则，否则总量不守恒。

**方案（按需求比例配给，pro-rata rationing）：**

```
对每种投入品 g：
  R(g) = Σ_b  demand_b(g)                    // 所有建筑申报的投入需求
  A(g) = 可分配供给(g)                        // = 本 tick 产出 − 消费占用 − 库存
  若 R(g) ≤ A(g)： 全部满足，alloc_b(g) = demand_b(g)
  否则：           alloc_b(g) = demand_b(g) · A(g)/R(g)      // 等比削减
  shortageFactor_b = min over g of ( alloc_b(g)/demand_b(g) ), 无投入则 = 1
  实际产出_b = q_output · level_b · hireRate_b · shortageFactor_b
```

- 该规则保证 **Σ alloc = A**（物质守恒），且单建筑情形退化为文档的"80% → 80%"。
- 顺序依赖：投入分配依赖本 tick 产出，本 tick 产出依赖投入 → 采用 §6 派生的两阶段序贯结算（先按上一 tick 的可用量申报，再结算），并在 `sim.Tick()` 中显式断言守恒。
- **无库存假设**（1.0）：每 tick 产清，不建库存。若后续要库存，`A(g)` 增加 `stock_g` 项即可，接口不变。这是 V1.1 的可选扩展。

### 4.4 消费模型

```
财富等级 w：  wage ≤ 5 → 5;  5<wage<10 线性;  10<wage<20 线性;  wage ≥ 20 → 20
基准需求 q_g = lerp(DemandPer100k[w][group], per 100k 人口) · Pop/100000     // 按 w 的整数与小数部分插值
组内权重 w_i = S_i / (2·P_i)             S_i = 净供给（产出 − 中间消耗）
购买顺序：同组内 w_i 从高到低，直到需求满足或商品售罄
满足度 sat_group = 实际购得 / 需求
必需满足度 sat_nec = 加权(简朴衣物, 基础食物)
```

- **定价口径（T6）**：`P_i` 使用**本 tick 结算价**（与生产、工资同一 tick），保证会计恒等式闭环。
- `S_i` 的"净供给"= 本 tick 产出 − 本轮中间投入消耗，**必须 ≥ 0**，且在数据校验期拒绝负值来源。
- 权重 `w_i` 在 `P_i → 0` 时发散：`P_i` 下限 `priceFloor` 保证有限；`priceFloor = 0` 的配置在加载期直接拒绝。

### 4.5 人口动力学

文档原文"满足度 ≥ 75% → +5% / 0% → −20% / 之间线性插值 / 75% 时增长率为 0"存在内部不一致：若在 `[0, 75%]` 与 `[75%, 100%]` 分别线性，则 `sat=0` 处应得 `−5%×(75/25) = −15%`，而非 `−20%`。

**架构定义（显式、可测，T7）：**

```
sat ∈ [0, 1]
若 sat ≥ t0(=0.75):   r = hiRate · (sat − t0)/(1 − t0)      // sat=1 → +5%
若 sat <  t0:         r = loRate · (t0 − sat)/t0            // sat=0 → −20%
增长率按年率存储，每 tick 应用 r / ticksPerYear
Pop(t+1) = Pop(t) · (1 + r/ticksPerYear)
```

该式同时满足文档三条锚点（`+5% @100%`、`0 @75%`、`−20% @0%`），只牺牲"两段同一斜率"这一无法同时成立的表述。**参数全部外置**：若你要求严格"单一斜率 −20%/75%"，把 `growth.mode` 切成 `single_slope` 即可，无需改代码。

### 4.6 劳动力与工资

```
岗位需求 (per level, per cohort):  need[c] = 5000 · shares[c]         // 0.75 / 0.20 / 0.05
实际雇佣:                          emp[c]  = need[c] · level · hireRate
工资池:                            wagePool[c] += emp[c] · wage[c]
工资进入消费（每 tick 全额支出，储蓄率为 0，与文档一致）
调整:  利润率 < 0 → hireRate -= hireStep;  利润率 > 0 → hireRate += hireStep
       两者都被 [0,1] 钳制；hireStep 为年率，按 ticksPerYear 折算
```

**设计要点**：`need[c]` 与平台 `shares[c]` 是 3.0 的接缝——3.0 只需让 `emp[c]` 由"劳动力市场出清"决定，而非由 `hireRate` 直接给定。表格结构不变。

**利润率的定义（T8，必须先定）**：文档用"利润率"同时驱动扩建与解雇，但未给公式。架构定义：

```
revenue_b   = Σ_g  sold_b(g) · P_g
inputCost_b = Σ_g  alloc_b(g) · P_g
wageCost_b  = Σ_c  emp_b(c) · wage_c
profit_b    = revenue_b − inputCost_b − wageCost_b
margin_b    = profit_b / max(inputCost_b + wageCost_b, ε)      // 成本加成口径
```

采用**成本口径**而非营收口径，因为营收口径在价格趋零时会放大噪声（分母 → 0），导致扩建抖动。文档未规定，此处属架构补全，需你确认。

### 4.7 GDP

```
GDP = Σ_purchases (实际购买量 · 成交价)  +  Σ_buildings 现金池期末余额
```

按文档仅计实际购买量。**注意**：现金池计入 GDP 会使 GDP 对"现金池累积"敏感。

**三口径并存（架构决定，由 `params.gdp.mode` 选择默认）**：

```
GDP_doc        = Σ_purchases (实际购买量 · 成交价) + Σ_buildings 现金池期末余额   // 文档口径（支出法 + 现金余额）
GDP_flow       = Σ_purchases (实际购买量 · 成交价)                              // 纯支出法，剔除现金池
GDP_production = Σ_buildings (本 tick 产出价值) − Σ_buildings (本 tick 中间投入价值)  // 生产法
```

理由：README 的既有契约用的是**生产法**（`current-cycle output value minus current-cycle intermediate input value`），而 1.0 文档用支出法 + 现金池。两者在动态期必然不等价（差额 = 存货变动 + 现金池变动）。架构上三者都算出来，默认展示 `GDP_doc`（服从 1.0 契约），并把三者差额作为**回归指标**——差额异常增大即说明货币/商品守恒出了问题。

> 该三口径设计同时解决了 README §"GDP uses the production approach" 与本契约的冲突：不是二选一，而是把差异变成诊断信号。

## 5. 子系统设计

### 5.1 雇佣率状态机

```
每建筑：hireRate ∈ [0,1]，初始 1.0（文档未指定，取满编）
每 tick：
  1. production/labor 结算完利润
  2. 若 margin_b < 0:  hireRate ← clamp(hireRate − hireStep, 0, 1)
     若 margin_b > 0:  hireRate ← clamp(hireRate + hireStep, 0, 1)
  3. 记录 idleTicks： hireRate < 0.75 → idleTicks++；否则 idleTicks = 0
```

**抖动抑制（D13/R1 相关）**：`margin` 用 **EMA（指数移动平均，窗口可配）** 而非单 tick 瞬时值驱动决策，避免价格振荡期高频切换雇佣方向。窗口默认 3 tick，参数 `labor.marginEmaTicks`。

### 5.2 建造队列与建造力分配

```
队列为栈（后进先出）? —— 文档写"按队列顺序分配（栈结构）"，两者矛盾。
架构定案：分配顺序 = FIFO（先入先出），但【预警插队订单】插入队首。
理由：栈结构会导致老订单永久饥饿（starvation），与"总建造力按队列顺序分配"冲突；
     而文档真正要的语义是"新插入的建造部门订单要优先"→ 用显式插队表达，语义更清晰。

每 tick：
  power = Σ 建造部门产出（受原料短缺惩罚）
  按顺序对每个订单： grant = min(30, power); order.progress += grant; power -= grant
  从订单发起建筑的现金池扣款：cost = grant · unitPrice(power)    // 1.0：现金池扣的是建造力费用
  若 order.progress ≥ buildCost → 完工：level += units（受 land/max 约束）
  若队列预计完成时间 > queueWarnTicks(52) → 队首插入"建造部门"订单（每 tick 至多一次）
```

- **每工地每 tick 上限 30 建造力**是硬约束，直接决定 10,000 tick 能否收敛（见 §10.2 吞吐量验算）。
- 建造力本身是商品（`建造力`，零利润价 7,250 / 开局价 11,917，见 §10.3），因此建造力也参与市场出清：**建造部门产出进入市场供给，建造消耗构成需求**。架构上把"建造力"作为普通商品处理，但它的需求方是建造队列而非消费者——这一分支在 `market.Step()` 中显式处理。

### 5.3 土地与自给农场

```
arableTotal = 10,000  （谷物农场 + 棉花种植园 共用）
arableUsed  = level(谷物农场) + level(棉花种植园)
自给农场产出 = f(arableTotal − arableUsed)   // 文档给"每单位耕地 ×2 谷物、×1 织物、×0.5 服装"
```

**架构风险 R3**：文档说"未利用耕地自动生成自给农场"，但未给"每单位耕地对应几个自给农场"。若按"每份未利用耕地 = 1 个自给农场"，则开局 10,000 份自给耕地产出 20,000 谷物/tick，远超 100k 人口的需求，谷物价格会瞬间崩到地板价，专业谷物农场永不盈利 → 与"利润驱动扩建"目标冲突。

**处理**：把映射改为数据参数 `land.subsistencePerArable`（默认 0.05）与 `land.substrstencePopCap`，即"仅未被就业人口覆盖的部分才从事自给农业"，并纳入标定任务 T-1.0-14 用 1.0 收敛验收反推。**此项需你确认口径**。

### 5.4 AI 扩建策略

```
对每个建筑 b（按 margin_b 降序）：
  n_extra = floor( (margin_b − threshold) / 5% ) + 1       若 margin_b > threshold(=10%)
  units   = min( n_extra · autoScaleRate · level_b,  level_b · 10% )     // 单次 ≤ 总数 10%
  受 land / maxLevelCap / buildSectorCap 约束
  生成订单入队（并记录事件）
```

- `autoScaleRate`：文档"每超过 5 个百分点多扩 1 个"的"个"含义未定（1 个 = 1 级？1 座？）。架构定为 **倍数**（扩 `n_extra × 10%` 等级），参数化可改。
- **利润率阈值就是均衡利润率的上界（rev 4 定案）**：只要 `margin > 10%` 就扩建，则利润率必然被压到阈值，稳态 `margin ∈ [0%, 10%]`。**这不再是缺陷**——契约已把目标从"利润→0"改为"有界稳定"（§8.4 判据 A2）。因此本设计**不再需要** `zeroProfitMode`（把阈值设为 0 的严格版本）：把阈值降到 0 会让 10% 的扩建步长直接冲过均衡点，产生负利润并依赖缩编机制（§5.5）回补，收敛反而更慢。该开关保留仅作参数扫描的对照实验，**默认关闭**。
- **扩建的平滑（D14）**：单次扩建 ≤ 总数 10%，配合 ODE 阻尼，可避免阶跃过大引发持续性极限环（文档 §2.3 承认这是欠阻尼系统）。

### 5.5 缩编机制

```
若 idleTicks > decay.window(156)：每 tick level ← level · (1 − decay.rate)，直到 hireRate > 75%
```

- `level` 是定点整数：`×(1−5%)` 需保底为"至少减少 0 或至少 1 级"，否则小建筑会被舍入卡死不缩编。架构规则：**若 `level > 0` 且计算结果为 0 变化，则强制 `level -= 1`**（保证单调可达）。
- 缩编回收：是否返还建造力/现金？文档未说。**架构选择：不返还**（更符合"拆除"语义），并作为参数 `decay.refundRate`（默认 0）留口。

### 5.6 货币接口（为 1.2 预留）

1.0 只需要三个池与一次转账语义：

```
type Pool interface { Balance() Money; Add(Money); Sub(Money) error }
消费支出：wagePool → 各建筑现金池（按实际购买额分摊）
建造支出：building.cash → 建造力供给方（建造部门现金池）
```

1.2 替换为 `Bank` 时，在 `Transfer` 上插入：利息计提、存款/贷款、货币乘数、央行利率 → 不需要触碰任何 L2 系统。这是 D2 分层的主要收益。

## 6. 主循环（tick 管线，定稿）

文档 §8 的顺序存在**会计闭环缺陷**：工资在步骤 3 计入现金池、步骤 4 被消费，但步骤 3 只把**利润**计入现金池，工资的去向未定义——工资若不进消费池，货币就会凭空消失，GDP 无法守恒。架构修正如下（与原顺序的差异全部标注）：

```
Tick(n):
  ① 雇佣调整（基于 n-1 的 margin EMA）                    ← 对应文档步 1 的一半，提前以消除内生性
  ② 产能申报：每建筑按 hireRate 算产出潜力与投入需求          ← 文档步 2
  ③ 投入配给：按 §4.3 pro-rata 计算 alloc 与 shortageFactor
  ④ 确定实际产出（含自给农场虚拟产出、建造力产出）              ← 文档步 2
  ⑤ 工资结算：wagePool[c] = Σ emp·wage；计入 wageCost          ← 文档步 2 补充
  ⑥ 市场出清/ODE 积分 → 本 tick 结算价 P*                     ← 文档步 8+9 提前（修正）
  ⑦ 消费者购买：由 wagePool 出资，按 §4.4 成交，得实际购买量      ← 文档步 4（用本 tick 工资）
  ⑧ 建造力需求进入市场：建造队列申报需求，结算建造力成交          ← 文档步 5 的市场侧
  ⑨ 利润结算与现金池：profit 入池，工资与投入成本出池            ← 文档步 3
  ⑩ 建造力分配 → progress → 完工 level++                     ← 文档步 5+6
  ⑪ 缩编（idleTicks > 156 的建筑）                            ← 文档步 7
  ⑫ AI 生成新扩建订单                                         ← 文档步 10
  ⑬ 人口更新（满足度 → 增长率）                                ← 文档步 11
  ⑭ 不变量断言 + 事件日志 + 快照
```

**相对文档的三处关键修正（需你确认）：**

| 编号 | 修正 | 理由 |
|------|------|------|
| M1 | 把价格结算（文档步 8-9）从**末尾**提前到**消费之前**（本 tick ⑥） | 否则消费者用 `n-1` 的价格购买，同时 `n` 的价格又由 `n-1` 的供需决定，形成固定的"两拍"滞后，会使收敛判定与"利润→0"验收更难判定，且价格序列被人为延迟一拍 |
| M2 | 显式引入 `wagePool`，工资在同一 tick 花掉 | 补齐会计闭环；否则工资既不进现金池也不进消费池，货币不守恒 |
| M3 | 雇佣调整（文档步 1）拆成"决策用 n-1 的 margin EMA"，执行放在 tick 开头 | 消除"先看本期利润再决定本期雇佣"的内生性（会人为放大振荡） |

> 若你坚持完全照文档顺序执行，架构上把 `sim.Pipeline` 定义为一个**有序阶段数组**，阶段顺序由 `params.pipeline` 配置——这是为了让你能在不改代码的前提下对比两种口径。但默认走 M1-M3。

## 7. 数值与确定性策略

### 7.1 定点表示

| 量 | 类型 | 刻度 | 范围检查 |
|----|------|------|----------|
| 钱 `Money` | int64 | 1e-3 元 | ±9.2e15 → ±9.2e12 元，安全 |
| 数量 `Qty` | int64 | 1e-3 单位 | 同上 |
| 价格 `Price` | int64 | 1e-3 元/单位 | 开局价 810 元 → 8.1e5 |
| 比例 `Permille` | int32 | ppm | 0..1e6 |

- `float64` 仅用于 ODE 积分的**中间步骤**（RK4 的 k1..k4、除法、`sqrt`），进入状态前统一 `num.Round` 回定点。
- 该做法可复现的依据：`float64` 对 ≤2^53 的整数**精确**，我们所有定点值都远小于 2^53，因此"定点→浮点→定点"链路的每一步都是 IEEE-754 确定运算，跨平台（amd64/arm64）结果一致。
- **禁止**：`math.Pow/Exp/Log` 参与状态更新（跨平台 libm 有 ULP 差异）；若确需，必须先转定点近似表。注意 rev 3 的常弹性需求 `D = a·(P/P₀)^(−ε)` 与 `K(P)` 都含幂运算，应改为查表/定点近似，或仅在每 tick 重估一次 `K` 时求幂（不在 RK4 子步内）；稳定性判据用平方比较（`2.8²·m ≥ K·h²` 而非 `ω·h ≤ 2.8`）。

### 7.2 输出侧

- `report.csv`：每 tick 一行，列 = tick, 11 商品价格/供给/需求/E, GDP_flow, GDP_doc, 平均工资, 人口, 各消费组满足度, 总建筑等级, 现金池总额, clampEvents。
- `report.summary.json`：末 N tick 的均值/方差/趋势斜率 → 用于收敛自动判定。
- `report.events.jsonl`：订单、完工、缩编、政策冲击、不变量告警。

### 7.3 收敛判定（自动化）

```
对每个商品 g，取最后 20% 的 tick：
  相对波动 = std(P_g) / mean(P_g)
  利润信号 = |mean(margin_b)| for all b
判定"收敛" ⟺ 所有商品 相对波动 < tol.price(默认 2%) 且 所有建筑 |margin| < tol.margin(默认 2%)
输出未收敛清单（哪几种商品、什么量级）
```

这是验收 T-1.0-15 的判据，其**可执行定义已由契约 §8.4 的 A1–A6 六条取代**（rev 4）：原"运行 10,000 周期后利润接近零"不再是判据。要点变化：

- A2 用 `margin ∈ [-10%, +25%]` 的有界带取代 `|margin| < 2%`；
- A3 用"均衡点不再漂移"（`Δ(P/P_cost) < 1e-4`、`Δ(S/a) < 2e-4` 每周期）取代"价格收敛到 `P_cost`"；
- 新增 A6 建造队列不饥饿（队列非空 tick 占比 < 20%）。

rev 3 补充两点：

- 收敛目标值不再是抽象的"某个均衡价"，而是 `P → P_cost`、`S → a`；因此可用 `mean(P_g)/P_cost,g` 直接判断是否收敛到成本价（比值应落在 1 ± 2%）。
- 取值窗口 20% 必须长于瞬态：`t_settle = 4/|Re λ_slow|`，其中 `ζ ≤ 1` 时 `|Re λ| = ζ·ω`，`ζ > 1` 时 `≈ ω/(2ζ)`。**不能用 `4/(ζω)` 一把梭**——`ζ ≫ 1` 时它会乐观 `2ζ²` 倍（探针 `VC_Go/tools/spring_price_probe.js` 实验 6：文档参数下估 80 tick、实际 4×10⁶ tick）。

### 10.2 性能与吞吐量验算（关键，决定 10,000 tick 可行性）

**建造吞吐量上限**：每工地 30 建造力/tick。建造部门单级产出 15 建造力/tick，则 1 级建造部门只够支撑 0.5 个工地（15/30）。建造部门自身成本 100 建造力，且需要钢 25、铁 25、工具 20。

粗算：若目标是 10,000 tick 内把建筑总量从开局 ~50 级扩到 ~3,000 级，且平均建筑成本 600 建造力，则总建造力需求 ≈ `(3000−50)×600 ≈ 1.77e6`。10,000 tick 内需平均 177 建造力/tick → 需约 **12 级建造部门**持续产出（15×12=180）。而 12 级建造部门本身只要 12×100=1200 建造力即可建成。**结论：吞吐量在数量级上可行**，但前提是建造部门的原料（钢/铁/工具）不被挤占——这正是 R1/R3 的耦合点，必须做 T-1.0-14 的结构标定。

**求解性能**：11 商品 × 11 建筑 → 每 tick 计算量为常数级（~10³ 次乘加）；RK4 × nSub=10 → ~10⁴ FLOP/tick；10,000 tick → ~10⁸ FLOP，Go 下 **< 100 ms**。即便建筑类别扩到 100 种商品，仍在 1 s 内。**性能不是本项目的风险**，架构上不为此做任何妥协（例如不需要 SIMD、不需要 CGO）。

**门槛**：`BenchmarkFullRun` 10,000 tick 全流程 P95 < 200 ms；`sim sweep` 1,000 组参数在全核并行下 < 60 s。

### 10.3 规模杠杆标定（R8 详证 → rev 3 已定案）

**问题（原始诊断）**：文档给出的三张表（§3.1 初始价、§3.3 投入产出、§5 雇佣）各自自洽，但**互不匹配**。以谷物农场为例（文档数值，单级、满编、每周期）：

```
产出收入 = 50 谷物 × 2,400 元/谷物            = 120,000 元
工资成本 = 5,000 人 × 6.75 元/人               =  33,750 元
（无中间投入）
隐含利润率 = (120,000 − 33,750) / 33,750      ≈ +255%
```

**rev 3 定案：价格不再手填，改由生产侧反推。** 解法是 §4.1 的 Leontief 价格方程，把"初始价"这一列从设计输入改成计算结果：

```
p = (I − Aᵀ)⁻¹·l                    // 零利润价 P_cost
p = ((1−m)I − Aᵀ)⁻¹·l               // 统一利润率 m/(1−m) 的价格，m = 1/6 → 20%
A[i][j] = 投入量 / 产出量            // §3.3
l[j] = 33,750 / q_j                  // §5：5,000 人 × 6.75 元
```

判据与实测（`VC_Go/tools/leontief_probe.js`）：

| 检查项 | 结果 |
|---|---|
| `A` 的谱半径 | 0.50 < 1 ⇒ 存在正的零利润价，三张表**可行** |
| 谷物零利润价 | 675 元（与本节手算的 `33,750/50` 一致，互为验证） |
| 零利润价区间 | 675 ~ 7,250 元（建造力最高） |
| 文档初始价 / 零利润价 | 2.16 ~ 22.86，且极不均匀（住房 2.16、谷物 3.56、服装 15.24、高档服装 22.86） |
| 统一乘 (1+20%) 时的实际利润率 | 谷物 20%，但炼钢厂 4.7%、建造部门 5.5% ⇒ **低于 10% 扩建阈值** |

最后一行是关键：**"所有价格统一乘 $(1+\delta)$"并不能给出统一利润率**——工资不随价格缩放，投入越重的建筑利润率被稀释得越厉害。要开局利润率整齐，必须解加成价方程 `((1−m)I − Aᵀ)⁻¹l` 而不是缩放 `P_cost`。

**开局标定三步**（详见 1.0 文档 §3.4）：解 `P_cost` 并校验谱半径 → 解**加成价方程** `p = ((1−m₀)I − Aᵀ)⁻¹l` 得 `P_init`（`m₀ = 1/6` → 各建筑利润率恰为 20%）→ 需求标定 **`a = S₀·(P_init/P_cost)^ε`**，使 `t=0` 时 `E=0`。

> **Q13 已定案**：标定式**不是** `a = S₀(1+m₀)^ε`。后者只在"所有价格统一乘 1.2"时成立，而加成价方程下 `P_init/P_cost` 随中间投入比重变化（谷物/织物 1.200、煤 1.456、钢 1.599、建造力 1.644）。取表格 `P_init` 口径的理由：它使各建筑开局利润率**恰好 20%**（全部高于 §4.1 的 10% 阈值，AI 在 `t=0` 即开始扩建），而统一乘 1.2 会让钢只有 4.74%、建造部门 5.45%，开局不扩建。

**均衡路径（rev 4 修订）**：产能扩张到利润率归零的假想位置为 `S∞ = S₀(P_init/P_cost)^ε`——随中间投入比重而不同，不是统一的 `S₀(1+m₀)^ε`。**但 `S∞` 只是假想位置**：§4.1 规定利润率跌破 10% 即停建，故实际产能停在 `S∞` 之前，利润率停在 `[0%, 10%]`。由于各建筑开局利润率均为 20% > 阈值，`P_init/P_cost > 1.1` 恒成立，故 `S∞ > S₀(1.1)^ε` 恒成立——实际停建点严格早于 `S∞`。扩张窗口长短仍由 `ε` 主导。该区间是扩建阈值与缩编阈值定义的**结构均衡带**，与目标修订一致（契约 §8.4）。

**验收（T-1.0-20）**：

1. 加载数据时校验 `A` 的谱半径 < 1，不通过直接报错。
2. 输出 `P_cost`、`P_init`、`P_cost/旧初始价` 三张对照表，人工确认量级。
3. 开局 50 tick 内**每种建筑利润率都 ≥ 10%**（否则扩建不会启动），且无持续性亏损。
4. 收敛期（10,000 tick）内价格触地板时间占比 < 5%。

> **结论变更**：R8 原先被评为"本项目最大的可行性风险"，其根因是价格表与成本表脱钩。rev 3 把价格改为成本结构的函数后，该风险从"设计风险"降级为"数据校验项"——谱半径与开局利润率两项断言即可闭环。

## 14. 附录 B：README 参考实现档案与冲突台账

`README.md` 描述的是一个 **C++17 + Raylib、契约冻结在 2.0** 的实现（省份 LocalMarket / 国家 NationalMarket / 仓库物流 / 铁路 / 世界地图 GUI）。**该路线已废弃**（技术栈改为 Go，契约以 `VC_Go/docs/1.0 生产与市场模拟.md` 为唯一权威）。但 README 里有一批已被验证过的设计决策与验收纪律值得继承，故建立本台账逐条决断，避免"重新发明"和"继承错误"。

### B.1 逐项决断

| README 中的机制 | 决断 | 理由 |
|-----------------|------|------|
| **52 周 = 1 年**（`52-week demand`、`rolling 52-week means`、周度结算） | ✅ **采纳** | 唯一能同时满足文档"156 = 52×3"的时间语义（§4.0 / D9） |
| **GDP 用生产法**（产出价值 − 中间投入价值） | ✅ **采纳为第三口径** | 与文档支出法差异 = 存货 + 现金池变动，可作守恒诊断（§4.7） |
| **商品平衡恒等式**（`opening + production + receipts − dispatches − transfers − consumer use − construction use = closing`） | ✅ **采纳为 1.0 不变量 A1** | 这是把"货币/商品守恒"从口号变成可执行断言的最佳形式；1.0 无库存时退化为 `production = consumer use + intermediate use + construction use`。**T-1.0-13 直接实现该恒等式** |
| **国内建造队列 + 预算保留**（原子预留、取消只退未付、价格入队时锁定） | ✅ **采纳，1.0 范围** | 文档 §4.3 只写了"每建筑独立现金池"，缺少"跨订单不能重复花同一笔钱"的约束；README 这套规则是成熟解，直接补进 §5.2 |
| **私有资本家扩建 ≠ 玩家指令** | ✅ **采纳（架构原则）** | 与文档"AI 利润驱动扩建"一致；确立"玩家命令与私有经济行为分离"的边界，1.1 引入玩家时不必返工 |

### B.3 从 README 时代吸取的流程教训

1. **只有文档没有代码 = 契约漂移的温床**。本机工作区只有三份 `.md`、无 `.git`、无源码，而 README 描述一个"已有 2.0 GUI 与 headless 审计报告"的成品——这种"文档描述的能力"与"实际存在的产物"之间的落差，是本项目最大的流程风险。**对策**：T-1.0-01 起就把契约写成可执行测试；每个版本在二进制里嵌入版本常量并做启动自检（README 已示范它在 2.0 上吃过版本混乱的亏：*"The repository has no 1.1 or 1.2 branch/tag"*）。
2. **契约必须单一**。README 里同时存在"2.0 契约"、"1.1 面板"、"legacy LocalMarket playerCash 兼容路径"三种口径，导致后续无法判断哪条路径是权威。**对策**：本设计确立"`VC_Go/docs/1.0 生产与市场模拟.md` 为唯一权威"，README 降级为参考档案（已记录在文档头部）。
3. **可视化/地图容易吃掉全部预算**。README 的篇幅与复杂度高度集中在地理、配色、截图回归上，而这些对"经济是否收敛"零贡献。**对策**：1.0 明确把渲染列为非目标（§1.3），Web 面板推迟到 1.1 且只读导出数据。
